# minigo の理想と、改善のための探索アプローチ（初回: grafana）

日付: 2026-10-06。読み手: 作者本人。
対象: minigo `3b96a7e`、grafana `fa8d6e6`、grafana/clickhouse-datasource `52a1bbd`。

このレポートの主題は、**改善点やネックを継続的に見つけるための探索方法（アプローチ）**。前半の1〜4節は、コードと議論から組み立てた前提、理想、仕組みづくり。5節以降は、選んだアプローチ（実在のコードベースに同期ツールを書く。初回は grafana）を一度試し、実際に改善点が出てくるかを確かめた記録。

## 1. 背景

作者の3つの投稿が起点。

- foo言語でfoo言語を書くために、foo言語のインタプリタを書く。インタプリタは表面をなぞるように動き、importを事前に解決しない。エントリーポイントは自由で、エコシステムはフルに使える。
- `go` との勝負は「ビルド速度＋起動速度＋実行速度」の和で行う。対象領域は go/packages などが遅い領域。そのために、stdlibのスタブやASTの取り出しといった機能を持たせている。
- 既存言語のASTの加工に囚われている。analyzerやLLMの出力で後から同期するのと、codegenのどちらが良いかは分からない。SSOTをクリーンに作れるのは、新規開発か腕力があるときだけ。

実装面での前提（README と `docs/sketch/plan-*.md` より）:

- **実行のしくみ:** パッケージは事前にインデックス化するが、関数は実行が到達した時点でバイトコードにコンパイルする遅延型のスタックVM。未実装の構文があってもコンパイルは失敗させず、実行が到達したときだけ trap する。
- **スクリプトは正しい Go:** gopls や vet がそのまま効く。特殊形式（quoted Go）とスタブパッケージによって、型付きの Go を AST としてホストに渡せる。`minigo.dev/inspect` を使えば、パッケージや宣言を値ではなく構文として眺められる。
- **import の解決:** `go.mod` / `go.work` と GOMODCACHE を使う。`go list` やダウンロードは使わない。cgo と、`unsafe.Pointer` による読み替えは対象外。
- **実行速度は非目標**（README に明記）。
- **examples:** task-run、convert-define、gen-sync、minigo-generate、test-detect。どれも「Go のソースをデータとして扱う」開発用の道具。

## 2. 理想と存在領域（対話で確認した理解）

- **対象はレガシーコード。** 新規開発なら protobuf のようなスキーマを起点にしたSSOTを作れる。既存のコードベースでは、Goのコード自体が事実上のSSOTになる。それとOpenAPIのドキュメント、pluginのマニフェスト、フロントエンドの型といった他の成果物との同期が、不完全なまま残っている。同期ツールには入力としてGoのコードが必要で、その解析をminigoが担う。
- **LLMとの関係。** LLMから得られるのは生成物で、同期が完全であることを保証するにはanalyzerのような検査が要る。すべてをLLMに読ませると、読ませた分だけトークンがかさむ。minigoは、決定的で安価に、繰り返し実行できる抽出や同期の道具を、Goで書いてすぐに動かすための土台になる（LLMはスクリプトを書く側に回る）。
- **遅延読み込み。** 読み込みを省けるのは表層の解析によってのみ。これは、go/packages や go の「全部を読み込み、全部が整合して初めて使える」ことへのフラストレーションから来ている。
- **速度。** 勝負するのはビルド・起動・実行の合計時間。痛みが出始める目安は、**キャッシュなしで3分前後**。

### 評価軸と最低水準

| 段 | 内容 | 測り方 |
|---|---|---|
| 動く（健全な状態） | 依存がそろったコードで、タスクが最後まで走る | `go run` の同じプログラムとの出力の diff |
| 動く（不完全な状態） | モジュールが足りないなど、goのツールチェーンが止まる状態でも動く | オフラインかつ依存不足の状態で比較 |
| 速い（主軸） | 合計時間が、go/packages 系の代替より短い | キャッシュあり・なしの実時間（`GOCACHE` は一時ディレクトリに向ける） |
| わかる | 止まったときに、どこで・なぜ止まったかが読み取れる | trap・traceback・CLIの使い勝手 |

## 3. 既存の探索の仕組みと、その空白

| 仕組み | 問い | 見えるもの |
|---|---|---|
| difffuzz（`tools/difffuzz`） | 言語仕様の各点で go と一致するか | 生成したプローブ、`$GOROOT/test` |
| casefuzz（skill） | 手書きのシナリオが動くか | 1プログラム単位のユースケース |
| minigo-usecasefuzz | 人が普通に書くプログラムが動くか | テキスト処理やスクリプト用途の27本 |

どれも「**Go として正しく動くか**」を測っている。2節の理想、つまり「**実在のレガシーコードを入力にした同期ツールが、go/packages より安く動くか**」を直接は測っていない。

- **入力の規模と汚さ:** 依存が数百あるモジュール、手元のキャッシュに足りないバージョン、`init` の連鎖など。
- **合計時間の比較:** go/packages を使う代替ツールとの比較。
- **`inspect` の網羅性:** 同期に必要な情報（関数本体、浮いたコメント、定数の初期化式）が表層の API で取れるか。

## 4. 探索・改善のためのアプローチ

### 4.1 候補

1. **realworld 同期タスク（採用）:** 実在のコードベースを固定のコミットで取得し、そこに「Goのコード × 別の成果物」を突き合わせる同期スクリプトを書く。`go run` 版（oracle）と minigo 版を比べ、出力・時間・止まった箇所を記録する。理想の全軸（動く／速い／わかる、表層だけで済むか）を一度に測れる。
2. **GOROOT の実在パッケージを corpus にする:** `go/scanner`、`go/ast`、`text/template` などに小さな入力を与えて `go run` と比較する。言語機能の生成器では出てこない慣用表現を拾える。1 を進める中で、派生として必要になる。
3. **LLM をユーザーとして使う:** 同じ同期タスクを、LLMに直接やらせる場合と、LLMが minigo スクリプトを書く場合とで比べる（トークン量と再現性）。LLMとの分担という主張の裏付けになる。
4. **遅延の可視化:** 読み込んだパッケージ数と状態を出す計測フラグ。1 の「なぜ遅いか／なぜ init が走ったか」を数字にする。

### 4.2 なぜ grafana から始めるか

- アプリケーションのコードで、依存が多い（`go.mod` が約700行、`go mod download` で約5GB）。`pkg/api` はキャッシュなしの `go vet` で101秒かかり、2節の痛みの目安に近い規模。
- 同期が必要な成果物がそろっている。OpenAPIの spec（`swagger:route` から go-swagger で生成）、同梱 plugin の `plugin.json`、外部 plugin（Goの設定構造体とTypeScriptの設定型）。
- 同梱 plugin は整合しているので、**外部の plugin も対象に含める**必要がある。初回は clickhouse-datasource を使った。

### 4.3 仕組み（繰り返し実行するための置き場所）

- **ハーネス（機械的に再実行する部分）:** `podhmo/minigo-usecasefuzz` の `realworld/` に置く。
  - `targets.tsv`: 名前、URL、固定するコミット。
  - `tasks/<name>/`: `go run` と minigo の両方で動くスクリプト。`inspect` を使うため minigo でしか動かないタスクは、golden ファイルと比較する。
  - `run.sh`: 準備 → 実行 → 判定（PASS / DIFF / TRAP）と時間を表にする。`GOCACHE` は常に一時ディレクトリに向ける。
  - 依存が大きく遅いので、minigo の `make test` には入れない。
- **手順（判断が必要な部分）:** minigo 側に skill `.claude/skills/realworld` を置く。手順は次の通り。
  1. ハーネスを実行する。
  2. 止まったタスクを最小再現まで絞り込む。
  3. 最小再現を `testdata/difffuzz` の PENDING と TODO.md に振り分ける。
  4. 新しいタスクやコードベースを追加する。
  5. 1回分の結果をこの `docs/sketch/ja/` にレポートとして残す。
- **重い探索は外、軽い回帰は内:** 最小再現だけが minigo 本体に入る。

## 5. 初回実行の結果

### 5.1 書いたタスク

- **A. grafana-openapi:** `pkg/api/api.go` のルート登録（関数本体の中にある `r.Get(...)` や `Group(...)` のネスト）と、`// swagger:route` コメントを照合する。`go/parser` で記述。
- **B. grafana-coreplugin:** `coreplugin` の plugin ID 定数と、`plugin.json` の `backend` を照合する。`go/parser` で記述。
- **B'. clickhouse-settings:** Goの `Settings` 構造体の json タグと、TypeScriptの `CHConfig` を照合する。`inspect` で記述。

### 5.2 動作と時間

| タスク | minigo | 比較対象 |
|---|---|---|
| A（出力は native と一致） | **5.4秒** ※仮修正3件を当てた状態 | ビルド済みバイナリ 0.21秒 / `go run` キャッシュなし 6.85秒・あり 0.27秒 / go-swagger の spec 生成 14.3秒・RSS 5.9GB |
| B（出力は一致） | 0.085秒 | 同梱 plugin のずれは `TestDataAlias` のみ（意図通り） |
| B'（`inspect` 版） | **0.031秒**。依存モジュールがキャッシュにない状態でも完走（パッケージの状態は `indexed` のまま） | `go vet ./pkg/plugin`: オフラインでは即失敗 / キャッシュなし 18.4秒 / あり 0.30秒 |

B' では、Go側にしかないキーが7件、TypeScript側にしかないキーが13件見つかった（意図的なずれも含む）。

### 5.3 読み取れること

1. **理想が一番きれいに成立したのは B'。** 表層だけで済むタスクなら、依存が欠けていても数十ミリ秒で終わる。
2. **A では minigo の優位が消える。** 必要なのは stdlib の `go/parser` だけなので、普通の `go run` も go/packages を使わない。比較の土俵がインタプリタの実行速度になり、native の約25倍かかった。
3. **同期に必要な情報が `inspect` から見えない。** 関数本体、浮いたコメント、定数の初期化式がそれにあたる。そのため `go/parser` を解釈する遅い経路に落ちる。

### 5.4 見つかった問題（すべて TODO.md に記録済み）

| 問題 | 影響 | 状態 |
|---|---|---|
| 暗黙の `&v` レシーバで `*s = T{...}` が消える（**結果を黙って間違える**） | `go/parser` がどんな入力でも落ちる | 原因特定済み・仮修正（スクラッチ） |
| ジェネリクスの推論が、要素の動的な型で `N` を束縛する | `ast.Inspect` / `ast.Walk` が全滅 | 原因特定済み・仮修正（スクラッチ） |
| `filepath.Split` がない | `go/scanner` が trap する | 既知の no-fall-through 問題 |
| `inspect.Value` で定数を読むと `init()` が走る | `log/slog` → `unsafe` まで連鎖して trap | 未着手 |
| `reflect.StructTag.Get` がない | タグを使う同期スクリプトがすぐ止まる | 未着手 |
| 診断（traceback が1行にエスケープされる、再panicで元の発生箇所が消える、`-h`・ファイル指定が不可） | 原因の特定に GOROOT のソースのコピーと二分探索が必要だった | 未着手 |

ハーネスでの再実行（main の minigo）: clickhouse-settings は PASS、grafana の2タスクは TRAP。仮修正版では3つとも PASS。

アプローチの評価: 初回の3タスクだけで、既存の difffuzz や usecasefuzz では出ていなかった「結果を黙って間違える」不具合が2件と、`inspect` の設計上の空白が見つかった。続ける価値がある。

## 6. 改善ポイント（根拠 / 阻害している理想 / コスト）

1. **`inspect` に関数本体・コメント・初期化式の構文ビューを足す:** 根拠は 5.3-3。阻害しているのは表層だけでの解析と合計時間。コストは中程度で、新しい仕組みが必要。
2. **`go/ast`・`go/parser`・`go/token` をホスト側にバインドする:** 根拠は A の5.4秒。既存の Go の解析資産を流用できる。ASTの値をスクリプト側にどう見せるかの設計が要る。
3. **結果を黙って間違える2件を正式に修正する:** difffuzz の PENDING に固定して fix ループに乗せる。暗黙の `&v` レシーバは、変数自身のセルを渡す根本的な修正が残っている。
4. **定数を読むときの値の層を `init` から切り離す。**
5. **バインドしたパッケージで、未定義メンバーをソースにフォールバックさせる:** 既存の TODO の優先度を上げる。
6. **診断を整える:** traceback の整形、再panic時の元の発生箇所の保持、`-h`、ファイル指定。

## 7. あると便利な機能

- `inspect` の式ビュー（評価せずに `Text` だけを返す）。
- 照合用のヘルパー: 構造体タグの解析、パスのパラメータの正規化、2つの集合の差分表示。
- `-check` の規約（終了コードと差分の出力形式）の共通部品化。
- 読み込んだパッケージとその状態をダンプするフラグ（4.1-4）。

## 8. あると便利な応用例（examples 候補）

- **openapi-sync（A）:** go-swagger の重い spec 生成の前段に置く、軽量なドリフト検出。
- **plugin-settings-sync（B'）:** Grafana の plugin エコシステム全体に横展開できる。
- **registry-sync（B）:** `init` に触れずに読めることを示す見本になる。
