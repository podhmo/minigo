# gen-sync: 壊れた入力・壊れた定義への振る舞い検証実験

対象: `examples/gen-sync`（`script/main.go` + `scanx/` + host `main.go`）
基準: 「エージェントに親切なツールとは、直接書く場合に得られていたフィードバック（どこが、なぜ、誰のせいで壊れたか）を、入力側の語彙で返し直してくれるツール。そして、それができないときに、成功したふりをしないツール」

---

## 1. 方法

`examples/gen-sync` を丸ごと /tmp に複製（go.mod の `replace` を絶対パス化）して退避させ、fixture `app/` ・ヘルパ `scanx/` ・スクリプト・環境（go.mod/引数/パーミッション）を順番に壊して実行する。各ケースで「終了コード」「最初のメッセージ行」「実際に書き込まれた内容」の3点を記録した。

複製側が `github.com/podhmo/minigo/examples/gen-sync` という import path 空間を本家リポジトリと共有するため、モジュール解決のフォールバック現象（後述 S4 群）も観測できた。本家リポジトリ内で実行する通常利用では同一ツリーが2回解決されるだけなので、現象の大半はそこでも再現する。

評価の軸:

- **語彙**: 失敗が「スキャン対象のファイル:行・decl 名・import path」で説明されるか（よい）、それとも `runtime trap` + スクリプト内 traceback などエンジン語彙に埋もれるか（悪い）
- **帰責**: 「フラグを直せ」「入力ファイルを直せ」「ツールのバグ」が区別できるか（convert-define の README「Reading a failure」表が理想形）
- **正直さ**: 処理できなかったとき exit≠0 で落ちるか。`0 file(s) updated` / `N file(s) updated` exit 0 のまま出力を欠落・退行させないか

## 2. 結果一覧

凡例: ✅ 語彙・帰責とも良好 / ⚠️ 落ちるが語彙が悪い / ❌ 成功のふり・静かな退行 / ℹ️ Go セマンティクスと一致する静かな振る舞い

### 2.1 呼び出し・環境まわり

| ケース | 結果 | 観測 |
|---|---|---|
| `./nope`（dir 不存在） | ⚠️ exit 1 | `runtime trap: resolve dir "./nope": entry directory "./nope" not found: stat ... no such file or directory` + traceback。行き先は分かるが「引数を直せ」とは言わない |
| `./app/status.go`（dir がファイル） | ⚠️ exit 1 | 同上だが末尾が `not found: %!w(<nil>)`。**エンジン側のフォーマットバグ**（resolve/goscan.go の `%w` に nil が来る） |
| go ファイルのない dir | ⚠️ exit 1 | `no buildable Go source files in <dir>` — `go build` と同じ語彙 |
| `_test.go` のみの dir | ⚠️ exit 1 | 同上（`_test.go` 除外は Go と一致） |
| モジュール外の dir (`/tmp/outside/pkg`) | ❌ exit 0 | **モジュール外のファイルにそのまま managed block を書き込んだ**。走査範囲はサブツリー内と説明されているが入口 dir 自体は無制限 |
| 余分な位置引数 `./app ./extra` | ❌ exit 0 | 2個目以降の位置引数を無言で捨てて `./app` を走査 |
| `./app -check`（フラグが後置） | ❌ exit 0 かつ**書き込み** | flag パッケージの仕様で `-check` が位置引数化し、かつ捨てられる。**check のつもりで managed block が書き換わる**危険なパターン |
| 未知フラグ `-bogus` | ✅ exit 2 | usage を stderr に出して落ちる |
| go.mod 削除 | ❌ exit 0 | 走査は続行し、サブツリーが全く解決しない**退行した出力で managed block を書き換えた**（graph.go の Remote/BoundRef、events.go の mood.Signal/shade.Ghost が消える）。「モジュール外」は合成 path `<dir>...` になっているが利用側からは見えない |
| go.mod の module path を別名に書換 | ❌ exit 0 | 全ファイル up to date と報告。実際には replace 先の**別ツリーのソース**で decl を解決して見かけ上正しい出力を出した（S4 参照） |

### 2.2 走査対象パッケージの破損

| ケース | 結果 | 観測 |
|---|---|---|
| `func Broken( {` 追記（構文エラー混入） | ⚠️ exit 1 | `parse <file>: <file>:43:14: expected ')', found '{' (and 3 more errors)` — ファイル:行:列は入力語彙だが `runtime trap` + traceback つき |
| `package` 節のないファイル | ⚠️ exit 1 | 同上（`expected ';', found 'EOF'`） |
| 未閉じバッククオートタグ | ⚠️ exit 1 | 同上（raw string literal not terminated） |
| 関数本体内の型エラー（`undefinedVar`） | ✅ exit 0 | `requiredgen` を正しく推論。**parse コストのみで読む設計の強み**が出ている |
| 同名 type の重複宣言（rename 途中） | ℹ️ exit 0 | Go なら redeclared エラー。両ファイルに同じ `stringer -type=Mode` が入る。重複は無言 |
| フィールド型が削除済み（`*Gone`） | ℹ️ exit 0 | `Gone` は解決不能として reach が素通り → `Ref` は directive を得ない。**理由の可視化なし**：型を消したのかタグを消したのか区別できない |
| 削除済み enum 型を参照する const 群 | ℹ️ exit 0 | 同上。沈黙で何も起きない |
| import cycle (a→b→a) | ✅ exit 0 | BFS が visited で止まり正常終了 |
| ジェネリクス `List[Marked]` 経由の required | ✅ exit 0 | インスタン化引数の `Marked` まで reach が辿り `requiredgen -type=Holder` を正しく推論 |
| 混在パッケージ `package app` + `package other` | ❌ exit 0 | **2パッケージを併合して走査**し、`other` の decl に対して directive を書き込んだ。Go では `found packages app and other` エラー |
| `extpkg` + `extpkg_test`（Go 合法レイアウト） | ❌ exit 0 | 同様に併合。`extpkg_test` 側 decl に `requiredgen -type=B` が入るが、`go generate` 実行時に `B` は `extpkg` パッケージに存在しない。**下流のツールが必ず解決に失敗する directive を生成** |
| `//go:build ignore` 付きファイル | ℹ️ exit 0 | index から素通り（Go と一致）。decl が消えても通知なし |
| `//go:build go1.30`（module lang より新） | ℹ️ exit 0 | 同上 |
| `// Code generated by mockgen. DO NOT EDIT.` ファイル | ❌ exit 0 | 生成ファイルの decl をスキャン対象に含め（`MockEnvelope` が `-variants=` に混入）、さらに **DO NOT EDIT ファイルへ managed block を挿入**。2つの生成ツールが同一ファイルを奪い合う形に |

### 2.3 依存パッケージの破損（-deps 含む）

| ケース | 結果 | 観測 |
|---|---|---|
| 依存 dir ごと削除（`internal/mood`） | ❌ exit 0 | **削除したパッケージの decl が出力に残った**（`mood.Signal` が `-variants=` に残存、`Remote` が requiredgen を保持）。import path 解決が replace 先の別ツリーへフォールバックし、消したはずのファイルを読んでいた（S4） |

| 依存パッケージに構文エラー（フォールバックなし経路） | ⚠️ exit 1 | `parse <file>: <file>:line:col:` で trap — 別ツリーがなければ正しく落ちる |
| 依存 import のパス自体が不存在 | ⚠️ exit 1 | `resolving import "...": import path "..." could not be resolved. Current module is "..." (root: ...)` — パスとモジュールを名指し。ラップが4重で読みづらい |

### 2.4 ファイルシステム・出力側の失敗

| ケース | 結果 | 観測 |
|---|---|---|
| 書き込み先が読み取り専用 (chmod 444) | ❌ exit 0 | `gen-sync: <path>: open <path>: permission denied` を **stdout** に出力し `9 file(s) updated` exit 0。**そのファイルは古いままなのに成功扱い**。CI の `-check` でも同様（書き込まないが読み込み失敗を drift カウントしない） |
| 走査対象ファイルが読めない (chmod 000) | ❌ exit 0 | **ファイルが出力行すら出さずに消える**。さらにそのファイルの import 辺も消え、`internal/envel` が未訪問 → `events.go` の `-variants=` から `shade.Ghost` が脱落し**managed block が退行した内容で書き換わった**。`1 file(s) updated` exit 0 |
| `inspect.DirOf` が別ツリーを指す (`./scanx`) | ❌ exit 0 かつ**越境書き込み** | 表示・書き込み先が `../../../home/.../repos/minigo/examples/gen-sync/scanx/scanx.go`。dir 引数で指定したディレクトリ**ではない**ファイルを編集した（パッケージキャッシュが import path キーで先行ヒット） |

### 2.5 managed region まわり

| ケース | 結果 | 観測 |
|---|---|---|
| managed run 内に手書き directive を挿入 | ❌ exit 0 | DO NOT EDIT とはいえ `//go:generate handtool ...` を**無言で削除**。`rewrote managed block (1 directive(s))` では削除された行が見えない |
| sentinel を2行に複製 | ℹ️ exit 0 | 先頭 sentinel で run を再生成。2個目の sentinel+directive は tail として残存 → **以後常に2つの managed block を持つファイル**になる（以降の run は安定） |
| CRLF ファイルに sentinel あり | ❌ exit 0 | `leadingComment` の `TrimRight` が `\r` を除去しないため **CRLF sentinel を認識できず新しい managed block を二重挿入**。以降は LF sentinel が先に当たるので安定化するが、重複 block は残る |
| CRLF ファイルへの書き込み | ℹ️ exit 0 | 挿入行は LF、既存行は CRLF の**混在行末ファイル**が生成される |
| stale directive が消える経路 | ℹ️ exit 0 | `retired.go rewrote managed block (0 directive(s))` — 消えた行名・消えた理由は一切出ない。「何を」「なぜ」消したかが分からない |
| `-check` の drift 表示 | ℹ️ exit 1 | `drift: 7 directive(s) out of sync` は**期待個数**であって差分ではない。追加なのか削除なのか退行なのか区別できない（E3 の実例では variants 脱落も同じ表示だった） |

### 2.6 ツール自身の定義の破損

| ケース | 結果 | 観測 |
|---|---|---|
| `script/main.go` に構文エラー | ✅ exit 1 | `parse <file>: <file>:line:col:` — **最も整形されたエラー**（traceback なし、単独行）。壊れた場所が分かる |
| `scanx` に構文エラー | ❌ exit 0 | import path 解決が別ツリーの scanx を読み、**壊れたヘルパを完全に見えなくした**（S4） |
| スクリプトが不存在パッケージを import | ⚠️ exit 1 | `import <path>: resolve <path>: resolving import <path>: import path <path> could not be resolved...` — パスが4回出る。traceback は `func Main` 宣言行（import 文の行ではない）を指す |

### 2.7 モジュール解決のフォールバック（S4：横断的な根本原因）

`mood` の実験で確認した挙動:

- `github.com/podhmo/minigo/examples/gen-sync/app/internal/mood` は**メインモジュール**（/tmp 複製）の dir でも、`replace github.com/podhmo/minigo => /repo` の**依存モジュール**側（/repo/examples/gen-sync/app/internal/mood）でも prefix 一致する
- 観測: import path 解決は**依存モジュール側を先に試し、見つからなければメインモジュール側**に落ちる。`inspect.Implementers` の内部で使われる `inspect.SourceOf(import path)`、スクリプト自身の `scanx` import、`DirOf` 後の `e.pkgs[path]` キャッシュヒット、すべてがこの経路を通る
- 結果: 「ローカルで消した/壊した」はずのパッケージが**別ツリーの生きたコピー**から読まれ、静かに古い decl が出力に混ざる（B6/D2/M2）。dir 引数で指定した場所と import path 空間がずれたとき、`./scanx` の例のように**別ツリーへの書き込み**にも繋がる（H1）

この挙動は「入力の語彙」以前の問題で、ツールが見ている世界がユーザーの指したディレクトリと一致していないことを**一切報告しない**。`go build` 相当の解決（メインモジュール優先、なければエラー）なら最初の2ケースは全てエラーになる。

## 3. 分析

### 3.1 「成功したふり」の構造

exit 0 で退行/欠落を残すケースは3系統に分かれる。

1. **I/O 失敗の握り潰し**（script 層）: `syncFile` の `os.ReadFile`/`os.WriteFile` エラーが `fmt.Println` に流れて `false` 扱い → 集計上「変わらなかった」→ exit 0（E1）。`-check` でも同じ握り潰しで drift 0 と誤判定し得る
2. **index へのサイレント脱落**（engine 層）: `ReadPackageFiles` の `ctx.MatchFile` が失敗したファイルは一覧から落ち、エラーにもならない → decl と import 辺が両方消え、**他ファイルへの書き込みまで退行する**（E3 → events.go の variants 脱落）
3. **解決のフォールバック**（resolver 層）: import path が別ツリーに解決されると、「消した/壊した」が見えないどころか**別ツリーに書き込みに行く**（B6/D2/M2/H1）

### 3.2 「入力側の語彙で返す」できていること・できていないこと

できている:
- パース/解決エラーは**ファイル名・行:列・import path をすべて含んで** trap する。convert-define のような「〜を直せ」接尾辞こそないが、行き先は分かる
- 型エラー混入・import cycle・ジェネリクス経由の required など、parse だけで答えられる範囲は頑健に動く（設計意図通り）

できていない:
- **ラッパーが全部 `runtime trap` になる**。引数ミス・入力破損・ツール内部バグが区別できず、convert-define の「誰が直すか」表に相当するものがない
- **「何故こうなったか」の経路がない**。`rewrote managed block (0 directive(s))` は「何が消えたか」を、`drift: N directive(s)` は「何がずれているか」を言わない。退行（variants 脱落）も正常なクリーンアップ（stale directive 除去）も同じ文言になる
- managed run の手書き行削除・`// Code generated` ファイルへの書き込み・混在パッケージ併合など、**ユーザーが引き起こした不整合を「正常」と見なして黙る**面が多い

### 3.3 見つかったバグ（改善候補のうち明確な欠陥）

- `entry directory %q not found: %!w(<nil>)` — resolve/goscan.go の `!st.IsDir()` 経路で nil error を `%w` に渡す
- CRLF ファイルで sentinel を見逃す（`leadingComment` の `TrimRight(" \t")` が `\r` を残す）→ 二重 managed block
- CRLF ファイルに LF 行を挿入して混在行末にする
- 後置フラグ（`./app -check`）が位置引数化して書き込み実行になる
- 位置引数2個目以降の無言破棄

## 4. 改善の方向性（stacked PR 候補）

優先度順。上2つが「成功したふりをしない」に直結。

1. **script 層: I/O 失敗を集計して exit≠0 にする**（E1）。ついでに dir の .go ファイル一覧と index の `inspect.Files` を突き合わせ、**index にない .go ファイルを明示**する（E3 の可視化 — 読めないならエラー、build 除外なら情報）
2. **書き込み先が走査 dir 配下であることを検査**（H1 越境書き込み防止）＋ モジュール外/合成 path の degraded 実行を警告（M1）
3. **変化した directive を報告する**（`dropped:`/`added:` 行）: stale 除去と退行が区別できるようになり、F1 の手書き削除も報告される（B1/E3/F1/-check 全部に効く）
4. **host 層: 位置引数は高々1つ**（C8/E2 の足元から直す）
5. **engine 層の小修正**: `%!w(<nil>)` を `not a directory` に。`leadingComment` の `TrimRight` に `\r` を足す（CRLF sentinel）
6. 残課題（このラウンドでは触らない）: resolver のメイン/依存モジュール優先順位（S4 の根本）、index 層の MatchFile 脱落の報告経路、混在パッケージ併合の方針、`// Code generated` ファイルの扱い、traceback の提示形
