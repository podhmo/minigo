# ハンドラーの HTML をブラウザで確認する: Go のテスト、minigo の直接実行、任意の補助ツール

対象は `examples/storybook`。目的は、適切な実データが手元にない状況でも、既存の Go アプリのハンドラーやレンダリング関数を指定したデータ・条件で呼び、その HTML を実ブラウザで描画しながら CSS やレイアウトを調整することである。位置づけとしては、SPA のコンポーネント開発で Storybook が担う使い方を、サーバー側でテンプレートを描画する古典的な MPA に持ち込むことに近い。HTML を生成して眺めること自体は手段であり、評価の基準は「描画して直す」反復がどれだけ楽になるかに置く（§8）。

最小の仕組みは、引数なしの `StoryXXX()` を minigo で直接実行して HTML を標準出力へ出すこと。storybook コマンドは、その仕組みに一覧・選択・配信を足す任意の補助ツールとする。

## 1. 何を確認したいのか

確認対象によって入口を選ぶ。

| 確認対象 | 呼び出すもの | 必要な準備 |
|---|---|---|
| データ取得、分岐、HTTP 応答を含むハンドラー | ハンドラー、またはアプリのルーター | ダミーの依存、request、recorder |
| 特定のデータに対するテンプレート出力 | レンダリング関数 | 表示用データ、出力先 |
| 実際の見た目 | 生成した HTML を開くブラウザ | HTML ファイルまたは配信先、必要な CSS・画像など |

ダミーの依存を差し込んでハンドラーを簡単に実行できるなら、通常の Go テストで確認すればよい。レンダリング関数へデータを渡すだけでよい場合も同様である。minigo を使うことを先に目的にしない。

`httptest.ResponseRecorder` での呼び出しは、ハンドラーの HTTP 入出力の検証である。実ブラウザで CSS・JavaScript・画像を読み込み、操作まで確認する E2E テストとは区別する。HTML の一致だけでも、見た目の正しさは保証されない。

## 2. Go だけでもできること

普通の Go テストからハンドラーやレンダリング関数を呼び、生成した HTML をファイルへ書けば、ブラウザで開いて確認できる。これが比較対象となる手軽な方法である。

- HTTP のステータス・ヘッダー・body を確認したいなら、request と recorder を使ってテストする。
- 特定データの表示を確認したいなら、レンダリング関数を直接テストする。
- 見た目を確認したいなら、得られた HTML をファイルへ出力して開く。必要ならそのファイルとアセットを静的配信する。

この例では `make native-html` が、同じ Story をネイティブの Go テストから実行し、HTML ファイルへ出力する。ネイティブ実行では、対象パッケージ全体が Go でビルドできる必要がある。また、テストには呼び出す関数への明示的な参照が必要になる。

HTML を生成すること、ハンドラーをダミーデータで実行すること、ブラウザで表示すること自体は、minigo 独自の機能ではない。

## 3. 最初の一歩: 引数なし Story の直接実行

Story は、表示条件を用意し、既存コードを呼び、結果を標準出力へ書く普通の Go 関数である。引数も戻り値も持たない。

```go
//go:build story

package app

import (
    "fmt"
    "strings"
)

func StoryUser() {
    var b strings.Builder
    if err := RenderUser(&b, &User{ID: "1", Name: "Alice"}); err != nil {
        panic(err)
    }
    fmt.Print(b.String())
}
```

これは render 関数（表示用データ → HTML）を呼ぶページ Story で、Story の主な形である（§8）。ハンドラー全体を確認する Story なら、同じ関数内で fake と request を作り、ハンドラーまたはルーターを呼ぶ。パスやクエリもその Story が条件として指定する。表示条件を変えたければ、Story のソースを編集するか別の Story を定義する。

以下のコマンドは `examples/storybook` で実行する。`minigo` コマンドが PATH にある場合は、storybook コマンドを経由する必要がない。

```sh
minigo run --tags story ./app StoryUser > /tmp/story-user.html
```

`/tmp/story-user.html` を本物のブラウザで開く。ブラウザの起動はこのコマンドの仕事ではない。

このリポジトリの minigo ソースから起動する場合は、次のように実行できる。

```sh
go -C ../../cmd/minigo run ./ run --tags story \
  "$(pwd)/app" StoryUser > /tmp/story-user.html
```

Go で起動するのは minigo CLI であり、対象の Story と、そこから呼ぶアプリのコードは minigo が解釈する。

### minigo を使う理由

- 指定したパッケージの関数を、名前を指定して呼べる。呼び出し用 main や Go のテスト関数を追加する必要がない。
- `package main` に置いたハンドラーや Story も呼べる。プレビューのために import 可能なパッケージへ分ける必要はない。
- 呼ばれない関数の未定義名など、Go のビルドを妨げる一部の未完成コードがあっても、必要な表示だけを確認できる。

ただし、選択したソースの構文解析、パッケージの初期化、実行する経路の解決は必要である。依存の init を省略できるという意味ではない。minigo に未対応の構文やライブラリ機能があれば実行できない場合もある。

## 4. アプリと表示用コードの境界

```text
既存の server main ── import ──> app

StoryXXX() ── 呼び出し ──> app のハンドラー／レンダリング関数
minigo CLI ── 名前で実行 ──> StoryXXX()

任意の storybook コマンド
    ├─ Story の探索と選択
    ├─ minigo で同じ Story を実行
    └─ HTML のファイル出力・ブラウザへの配信
```

既存の server main は Story・fake・storybook を知る必要がない。本番用の依存構築を、表示確認用の fake に置き換えない。

このサンプルで以前追加した固定データだけの `cmd/server` は、表示確認用サーバーをもう一つ作る構成になっていた。通常サーバーの起動例を示すために fake を持たせることは、ここで検証したい境界を曖昧にするため撤去した。現在の `app` はハンドラーとテンプレートの例であり、本番サーバーの起動・依存構築まで再現したものではない。

`Store` interface は、データ取得を差し替えられるようにしたアプリ側の設計である。minigo 固有の要件ではない。ダミーデータや fake の準備は Story またはテストに置く。

`story` ビルドタグは、表示用コードを通常の Go ビルドから除くための選択である。minigo が任意の関数を呼ぶために、常にタグが必要なわけではない。`Story` という名前の接頭辞は、補助ツールが探索するための規約である。

## 5. 必要になったら storybook を使う

Story が増えると、関数名の指定や HTML ファイルの管理が面倒になる。その段階で、探索・選択・配信を補助するコマンドを使う。

```sh
go run ./cmd/storybook -list ./app
go run ./cmd/storybook ./app StoryUser
go run ./cmd/storybook -o /tmp/storybook-out ./app
go run ./cmd/storybook -http 127.0.0.1:6006 ./app
```

HTTP モードでは `http://127.0.0.1:6006/` をブラウザで開き、一覧から Story を選ぶ。ツールは、直接実行と同じ引数なし Story を呼ぶ。

`cmd/storybook` は minigo をライブラリとして組み込んだ通常の Go コマンドである。`Book` は対象の `app` を import せず、対象ディレクトリを minigo で読み、指定関数を実行する。`minigo.WithOutput` で標準出力を捕捉し、その HTML を保存・配信する。HTTP request や recorder を Story へ注入する仕組みは不要である。

描画ごとに新しいエンジンを作るので、Story やテンプレートの編集は次のリクエストで読み直される。ファイル変更を監視してブラウザを自動リロードする機能とは別である。

### 独自コマンドで標準ライブラリにも fake を設定する

minigo をライブラリとして組み込んだ独自のプレビューコマンドなら、intrinsic を含む host binding を差し替えて、標準ライブラリへの呼び出しにも fake を与えられる。たとえば、表示に使う現在時刻を固定したり、外部 I/O に決まった結果を返させたりする実行環境を、呼び出し側で用意できる。対応する binding 経由の呼び出しなら、表示確認のためだけにアプリへ interface や依存注入の仕組みを追加する必要がない。

`Engine.Bind` は指定した import path の host パッケージを登録する API で、標準ライブラリのパスにも使える。既存の binding は `Engine.BoundOf` から取得できる。差し替えは対象コードの初期化・実行より前に行い、描画ごとにエンジンを作る構成では各エンジンへ設定する。パッケージ全体を再登録する場合は、対象コードが使う残りのシンボルも保持する必要がある。ソース解釈を強制する `ModeSource` は host binding を迂回するため、差し替えるパッケージの実行モードも考慮する。

差し替えが効くのは、minigo が解釈するコードから、その binding を通って行われる呼び出しである。コンパイル済みの host 実装内部で行われる標準ライブラリ呼び出しまで一律に置き換えるものではない。

これは minigo の既存 API を使った拡張方法であり、現在の `cmd/storybook` に fake binding を選択・設定する CLI 機能は実装していない。独自コマンドを作る理由には、一覧・配信の利便性に加え、アプリを変更せず表示用の実行環境を組み立てられることもある。

### stdout と HTTP 応答を混同しない

Story が出力するのは body だけである。元のハンドラーの HTTP ステータス・ヘッダーは stdout に含めない。

たとえば元のハンドラーが 404 を書いていても、補助ツールが HTML を正常に生成して配信できたことと、その 404 は別の事柄である。元の HTTP 応答を検証する場合はアプリのハンドラーテストを使う。Story の実行失敗は、補助ツール側のエラーとして扱う。

ブラウザで URL にクエリを追加しても、それを Story の request へ転送する controls は提供しない。引数なし Story は、自分自身で表示条件を完結させる。

### ブラウザで確認できる範囲

サンプルの HTML は自己完結した表示を中心にしている。実アプリの CSS・画像・JavaScript、相対 URL、フォーム送信やリンク先まで自動で再現するものではない。アセットが必要なら、それらの参照先と配信方法も用意する。補助ツールで一画面を表示できることを、アプリ全体の E2E 成功とはしない。

## 6. Makefile からの操作

`examples/storybook` から次を実行する。リポジトリルートからなら `make -C examples/storybook <target>` を使う。

```sh
make help
make render STORY=StoryUser   # minigo CLI で直接実行し、HTML を標準出力へ
make native-html             # Go テストで同じ Story を実行し、HTML ファイルへ
make list                    # 任意の補助ツールによる一覧
make export                  # 一覧と各 Story の HTML を出力
make preview                 # 任意の補助ツールでブラウザ向けに配信
make test
```

`make preview` はフォアグラウンドで動き、Ctrl-C で停止する。生成した HTML の保存先や各ターゲットのオプションは、`examples/storybook/Makefile` と README を参照する。

## 7. テストで保証すること、しないこと

| 検証 | 目的 | そこからは言えないこと |
|---|---|---|
| 通常の Go のハンドラーテスト | ダミーの依存と request に対する HTTP 入出力を確認する | 実ブラウザでの見た目・操作が正しいこと |
| ネイティブ Story と body の golden の比較 | 普通の Go として実行した表示用コードの出力を確認する | アプリ全体の本番環境が再現されていること |
| minigo の直接実行と同じ golden の比較 | storybook なしで Story を実行でき、選んだ条件の出力が一致すること | あらゆる Go コードで一致すること |
| `package main` と未使用の未完成関数を含む例 | import や全体の Go ビルドをプレビューの前提にしないこと | 実行経路や init のエラーも無視できること |
| 補助ツールの探索・出力・HTTP 配信 | 一覧から選んだ Story の HTML を取得できること | HTML の視覚的な正しさ、本番ルーターと同じ挙動 |

期待する HTML は `app/testdata/golden` に置く。native と minigo の一致を確認するための明示的な関数一覧は、Go 側の比較検証の都合であり、利用側のアプリへ要求するレジストリではない。

## 8. 現時点での評価と次の判断材料

小さな例で直接実行とネイティブの出力が一致しても、既存の実アプリで便利だと確認できたことにはならない。用例の適切さは次の順で判断する。

1. 通常の Go アプリのハンドラーやレンダリング関数を基準にする。
2. 表示条件の準備だけを行う小さな Story を追加する。
3. Go テストから HTML を出す方法と、minigo の直接実行の両方を試す。
4. アプリ本体の変更、追加コード、実行手順、編集から表示までの手間を比べる。
5. Story が増えたときだけ、一覧と常駐プレビューの利便性を評価する。

このサンプル自体は実験用に作ったアプリであり、自然な既存アプリをそのまま持ち込んだ検証ではない。特定の binding を通るように作った例だけで適用範囲を広く主張しない。

### 目的の再確認: MPA のための Storybook 的な使い方

#1065 のマージ後に目的を見直した。ハンドラーを名前で呼んで HTML を得ることは手段であり、本当にしたいのは、実データがない状況で実ブラウザに描画し、CSS やレイアウトを調整することである。

より正確には、SPA における Storybook の使い方を古典的な MPA に当てはめたものである。SPA ではコンポーネントが props だけで描画できるため、API サーバーや実データなしに状態ごとの見た目を並べられる。MPA ではページがサーバー側のハンドラーとテンプレートで組み立てられ、表示用データは DB・認証・セッションなどサーバー全体を通って初めて揃う。そのため「特定の状態の画面をブラウザで見る」ためにアプリ全体を起動し、データを仕込む必要があった。対応関係は次のとおり。

| SPA の Storybook | MPA での対応物 |
|---|---|
| コンポーネント | テンプレート（ページまたは部分テンプレート）とレンダリング関数 |
| props / args | テンプレートへ渡す表示用の構造体 |
| story（状態ごとの定義） | データ状態ごとの `StoryXXX()` |
| グローバル CSS・decorator・preview-head | アプリのレイアウトテンプレートと静的アセットの配信 |
| viewport addon | 幅を変えた iframe での並列表示 |
| モックした API 応答 | fake の Store、差し替えた binding、§9 の関数差し替え |

この観点で見ると、現在の例は次の点で調整作業のループを支えていない。

- **アプリの実際の CSS が当たらない。** サンプルの HTML は自己完結しており、§5 のとおりアセット配信は範囲外としている。実アプリは `/static/app.css` のような外部ファイルを参照するため、プレビューがアプリの静的ファイルを元と同じパスで配信しなければ、調整対象の CSS が読み込まれない。
- **Story の単位がハンドラーごとで、崩れやすいデータ状態ごとではない。** レイアウト調整で見たいのは、0 件・1 件・大量、長い名前や改行できない長い英単語、任意フィールドの欠落、画像なし、多言語混在といった状態である。「適切なデータがない」ことへの対処は、こうした状態を揃えた fixture を用意することにある。
- **状態違いを並べて比べられない。** CSS の一箇所の変更は複数の状態に同時に効く。1 Story = 1 ページより、同じテンプレートの状態違いと viewport 幅違いを一画面に並べる方が調整に向く。
- **変更の種類で必要な再実行が違う。** CSS だけの変更なら Go 側の再実行は不要で、ブラウザの再読み込みで足りるべきである。テンプレートや Go の変更では再実行が必要になり、ビルドなしで読み直せる minigo の性質が効くのはこちらである。

minigo 固有の価値になりうる候補は、表示用データの組み立てである。既存アプリの表示用構造体は深く入れ子になりがちで、実データは DB にある。テンプレートが使う型から「空・最小・最大・長文」の値を生成できれば、fixture の手書きを減らせる。ソースを必要な分だけ読む minigo の性質と相性がよい可能性があるが、未検証である。§9 のデータ取得関数の部分差し替えも、同じく実データなしで状態を再現する手段として位置づけられる。

### 補足: テンプレートより html tree を組み立てる関数の方が確認対象に近い

テンプレートを使わず、vdom を直接書くように html tree を組み立てる関数（`func UserCard(p UserCardProps) Node` の形）で画面を書くと、コンポーネント単位で確認しやすくなる。この Story で本当に確認したいのは、こうした関数単位のコンポーネントである。

- **props が型として表れる。** 描画に必要なデータが関数のシグネチャに現れ、Storybook の args にそのまま対応する。部分テンプレートでは `.` に何でも渡せるため、依存するデータが暗黙になる。
- **story がただの関数呼び出しになる。** 状態違いは引数を変えた呼び出しであり、レイアウトで包む・CSS を読み込むといった decorator も、Node を受けて Node を返す関数で書ける。テンプレート名の解決や `{{define}}` の管理は不要になる。
- **minigo と噛み合う。** コンポーネントは副作用のない Go 関数なので、名前で呼ぶ仕組みがそのまま使える。props の型がシグネチャにあるため、上で挙げた型からの値生成も「コンポーネントの引数の型から値を作る」と素直に定義できる。引数なしの Story から、引数を持つコンポーネントを直接呼ぶ形へ広げる道もある。
- **html/template に依存しない。** `template.FuncMap` や html/template の binding で発生した問題の経路を通らない。

ただし、既存の Go コードを事実上の正とする minigo の位置づけとは緊張関係がある。既存の MPA の多くはテンプレートで書かれており、それらには部分テンプレート単位の Story が引き続き必要である。html tree 方式は、新規に書く部分や移行先で推奨する書き方として扱う。大きなページの組み立てを minigo で解釈したときの速度は未測定である。

### Story の主な対象はハンドラーではなく render 関数

同じ考え方をページに当てはめると、ハンドラーは「表示用データを取得する処理」と「描画」を合わせたものであり、Storybook の意味でのコンポーネントは後者である。ページ単位のコンポーネントは `RenderUserPage(w io.Writer, v UserPageView)` のような render 関数であり、Story の主な対象はこれにする。

- **fake が要らない。** render 関数は表示用の構造体を受け取るだけなので、Story は値を組み立てて呼ぶだけで済む。Store の fake、request、recorder は不要になる。
- **SPA と同じ構造になる。** 部品もページも「props → HTML」のコンポーネントであり、その上にデータを取得して props を作るハンドラーが乗る。
- **型からの値生成の対象がはっきりする。** 生成すべき値は render 関数の引数の型と決まる。
- **ページ単位のテンプレートでも同じ利点がある。** html tree 方式でなくても、ページのテンプレートを表示用構造体で実行する render 関数が切り出されていれば、それを Story から呼べる。

ただし、render 関数を Story の対象にする価値は、`TestRenderXXX()` で render 関数をテストすることの延長にはない。出力した HTML を golden と比較しても、CSS やレイアウトが意図どおりかは分からない。価値は、データ状態ごとに render 関数を呼んで実ブラウザで描画し、CSS とレイアウトを確認・調整する作業にある。§7 の golden 比較は minigo とネイティブの実行結果の一致を確かめる回帰テストであり、この目的を担うものではない。

ハンドラーを対象にした Story は、render 関数が切り出されていない既存コードのための代替手段とする。§9 のデータ取得関数の部分差し替えは、この代替手段を支えるものと位置づける。example はこの方針に合わせて整理した。`RenderUser` と `RenderUserList` は `io.Writer` と表示用データだけを受け取る render 関数とし、HTTP ヘッダーやエラー応答はハンドラー側に残した。Story は 2 種類のファイルに分けた。

- `app/story_page.go`（主）: render 関数をデータ状態ごとに呼ぶ。通常のユーザー、悪意のある名前とタグなし、非常に長い名前と多数のタグ、複数件の一覧、0 件の一覧。fake の Store も request も使わない。
- `app/story_handler.go`（代替手段）: fake の Store と request でハンドラーを呼ぶ。成功、404、タグ絞り込みの 3 つ。

以前あった `StoryUserFromQuery`（request のクエリから表示用データを作る例）は、どちらの位置づけにも当てはまらないため削除した。host map の読み書きは、ハンドラー Story の `StoryListUsersByTag` が引き続き通る。ハンドラーテストの `/users` は、ページ Story の `StoryUserList` と同じ golden に一致する。ハンドラーが組み立てる表示用データと、Story が直接渡すデータが同じ HTML になることを示している。

次の検証は、まず静的ファイルの配信と状態違いの並列表示を足し、実際に CSS を調整する作業で使ってみることとする。型からの値生成は、fixture の手書きが負担だと確認できてから着手する。タスクは [TODO.md](../../../TODO.md) に記録する。

以前の文書では `html/template`、`template.FuncMap`、host map の読み書きなどの不足と対応、および編集ループの測定を時系列で記録していた。それらの実装履歴は Git の履歴から参照できる。本書の刷新後の構成について速度・メモリを再測定したわけではなく、古い測定値を現在の優位性の根拠として再利用しない。

## 9. Future work: ソース関数の部分差し替え

ハンドラーやテンプレートは元のソースを実行し、`loadUser(id)` のようなデータ取得関数だけをプレビュー側から fake に差し替えられると、表示確認のためだけにアプリへ interface を導入する必要を減らせる。Story や独自の実行コマンドが表示条件を用意し、既存サーバーの main やアプリ本体を変更せずに特定の状態を再現する用途を想定する。

現在の `Engine.Bind` はパッケージ全体を host パッケージとして登録する機能で、元のソースを残しながら一部の関数だけを上書きする API ではない。既存の host binding は `Engine.BoundOf(...).Globals.Set(...)` でシンボルを変更できるが、それをソース関数全般の部分差し替えとして保証しているわけではない。この future work は、そのための明示的な API と意味論を検討する未実装の課題である。

検討・検証する点は次のとおり。

- 対象を import path と関数名などで指定し、元の型・その他の関数・パッケージ状態を保つこと。
- 直接呼び出し、取得した関数値、メソッド呼び出しに差し替えが及ぶ範囲と、既に取得・コンパイルされた参照の扱い。
- 引数・戻り値の互換性、型エラーの報告、パッケージの初期化より前に設定できること。
- 設定を engine/session ごとに隔離し、並行プレビューや再描画へ意図せず漏らさないこと。
- 実行中の変更・解除を許可するか、ロード・実行前だけの設定に限定するか。
- コンパイル済み host 実装内部への呼び出しなど、差し替えられない境界を明示すること。

実装した場合は、interface を追加していないアプリで、元のハンドラーとテンプレートを実行しつつデータ取得だけを置き換える例を使い、通常の Go テストと準備・実行の手間を比較する。タスクは [TODO.md](../../../TODO.md) に記録する。
