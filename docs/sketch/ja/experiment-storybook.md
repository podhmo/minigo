# 古典的な MPA に Storybook 的な見た目調整を持ち込む（minigo を使った試み）

`examples/storybook` は、「実データが手元にない状態でも、Go で書かれた MPA の画面や部品を指定した条件でブラウザに描画し、CSS やレイアウトを調整しやすくできないか」というアイデアを、`minigo` を使って試してみた例である。

SPA の開発では、コンポーネントが props だけで描画できるため、API サーバーや実データがなくても状態ごとの見た目を並べて確認・調整する（Storybook のような）進め方が使われている。これと似た仕組みを、サーバー側で HTML を組み立てる古典的な MPA に持ち込めると便利そうなのではないか、という点を探っている。

位置づけとしては、HTML を生成してテストや golden と突き合わせること自体が目的ではなく、「実ブラウザで描画して CSS やレイアウトを直す」反復がどれだけ楽になりそうかを確かめる試みである。

## 1. MPA に Storybook を当てはめてみるとどう見えそうか

MPA では、ページはサーバー側のハンドラーとテンプレートで組み立てられ、表示用データは DB・認証・セッションなどを通って初めて揃う。そのため「特定の状態の画面をブラウザで見ながら CSS を直したい」と思うと、アプリ全体を起動してデータを仕込むところから始めなければならず、手間がかかりやすい。

SPA の Storybook で使われる要素を MPA に置き換えてみると、だいたい次のような対応になりそうに思える。

| SPA の Storybook | MPA で対応しそうなもの |
|---|---|
| コンポーネント | テンプレート（ページまたは部分テンプレート）と render 関数、あるいは HTML ツリーを組む関数 |
| props / args | テンプレートへ渡す表示用の構造体 |
| story（状態ごとの定義） | データ状態ごとの `StoryXXX()` |
| グローバル CSS・decorator | アプリのレイアウトテンプレートと静的アセットの配信 |
| viewport addon | 幅を変えた iframe での並列表示 |
| モックした API 応答 | fake の `Store`、実行時の binding や関数の差し替え |

もっとも、HTML を生成してブラウザで開くだけなら、通常の Go テスト（`httptest.ResponseRecorder` や render 関数の直接呼び出し）でファイルへ書き出す方法でもできる。ただ、通常の Go テストはパッケージ全体がビルドできる必要があり、テストコード自体に呼び出しを増やす手間もある。そこで今回の例では、Go インタプリタの `minigo` を使うとこの体験がどこまで軽くなるかもあわせて試している。

## 2. 最小の形: 引数なしの Story を minigo で直接実行する

ここで置いた最小の仕組みは、「表示条件を用意してアプリの表示コードを呼び、HTML を標準出力へ出すだけの引数なし関数 `StoryXXX()`」を書く、という形である。

```go
//go:build story

package app

import (
    "fmt"
    "strings"
)

func StoryUser() {
    var b strings.Builder
    if err := RenderUser(&b, &User{ID: "1", Name: "Alice"}); err != nil {
        panic(err)
    }
    fmt.Print(b.String())
}
```

表示条件を変えたければ Story の中身を編集するか別の `StoryXXX()` を足す。`minigo` が PATH にある場合は、`examples/storybook` から次のように関数名を指定して HTML を吐き出せる。

```sh
minigo run --tags story ./app StoryUser > /tmp/story-user.html
```

リポジトリ内の `minigo` ソースから動かす場合は次のようになる。

```sh
go -C ../../cmd/minigo run ./ run --tags story \
  "$(pwd)/app" StoryUser > /tmp/story-user.html
```

こうして出力した `/tmp/story-user.html` をブラウザで開く。アプリ本体との境界は次のように保てるので、既存の `server main` 側は Story や fake の存在を知らなくて済む。

```text
既存の server main ── import ──> app

StoryXXX() ── 呼び出し ──> app のハンドラー／レンダリング関数
minigo CLI ── 名前で実行 ──> StoryXXX()

任意の storybook コマンド
    ├─ Story の探索と選択
    ├─ minigo で同じ Story を実行
    └─ HTML のファイル出力・ブラウザへの配信
```

この形を `minigo` で試してみて感じたメリットはいくつかある。

- 呼び出し用の `main` やテスト関数を書かなくても、パッケージ内の関数を名前で直接呼べる。
- `package main` のまま置いたコードでも、プレビューのために別パッケージへ切り出さずに呼べる。
- 呼ばれない別の関数に未定義名などの未完成コードが残っていて Go 全体がビルドできない状態でも、確認したい表示経路だけ動かせる場合がある。

一方で、対象ソースの構文解析・パッケージ初期化・実行経路の解決は通る必要があるため、依存の `init` を丸ごと無視できるわけではないし、minigo 未対応の構文やライブラリに当たれば動かない点は踏まえておく必要がある。

## 3. Story の対象をどう切ると自然そうか

今回の例では、Story の対象として「render 関数」と「ハンドラー」の両方を試している。

- `app/story_page.go`（主）: `RenderUser` や `RenderUserList` のように `io.Writer` と表示用データだけを受け取る render 関数を呼ぶ。通常のユーザー、悪意のある名前・タグなし、非常に長い名前・多数のタグ、複数件の一覧、0 件の一覧などを書いている。
- `app/story_handler.go`（代替）: fake の `Store` と request を作ってハンドラーを呼ぶ（成功、404、タグ絞り込みの 3 つ）。

実際に書いてみると、やはり主対象はハンドラーではなく render 関数の方が自然だと感じる。ハンドラーは「データ取得＋描画」なので fake や request/recorder が必要になるが、render 関数なら表示用データを組み立てて渡すだけで済み、SPA の「props → 描画」と構造が揃うからである。ハンドラー向けの Story は、render 関数が切り出されていない既存コードを触らずに確認したいときの代替手段、という位置づけがしっくりきそうである。

### さらに進めるなら: テンプレートより HTML ツリー関数

テンプレートではなく、`func UserCard(p UserCardProps) Node` のように HTML ツリーを組み立てる関数で書ける場合を考えると、Storybook 的な仕組みとさらに噛み合いそうに見える。

- 描画に必要なデータが関数のシグネチャ（props の型）にそのまま表れる（部分テンプレートだと `.` に何でも渡せて依存が暗黙になりやすい）。
- 状態違いは引数を変えた関数呼び出しになり、レイアウトで包む decorator も `Node` を受けて `Node` を返す関数で書ける。
- `template.FuncMap` や `html/template` の事情を通らず、副作用のない Go 関数として `minigo` から扱いやすい。

もっとも、既存の MPA はテンプレートで書かれていることが多く、既存の画面にはテンプレート／部分テンプレート単位の Story が引き続き必要になる。HTML ツリー方式は新規の部品や移行先の書き方として相性が良さそう、という感触である（大きなページを `minigo` で解釈したときの速度はまだ測っていない）。

## 4. 補助ツール `cmd/storybook`: minigo をライブラリとして組み込む例

Story が増えたときに毎回関数名やリダイレクト先を指定する手間を省くため、探索・ファイル出力・簡易 HTTP 配信を行う `cmd/storybook` もあわせて作ってみた。

```sh
go run ./cmd/storybook -list ./app
go run ./cmd/storybook ./app StoryUser
go run ./cmd/storybook -o /tmp/storybook-out ./app
go run ./cmd/storybook -http 127.0.0.1:6006 ./app
```

（`examples/storybook` では `make list` / `make export` / `make preview` でも動かせるようにしてある。）

実装としては、`cmd/storybook` が対象の `./app` を直接 `import` するのではなく、`minigo` をライブラリとして組み込んで対象ディレクトリを読み込んでいる。指定された `StoryXXX()` を実行し、`minigo.WithOutput` で標準出力の HTML を捕捉してそのまま配信する。描画リクエストごとに新しい `minigo` エンジンを作る構成にしたため、Story やテンプレートを編集したあと再ビルドなしで次のリロードから反映される（ブラウザの自動リロード自体はまだない）。

### minigo 組み込みだからこそ見えそうな拡張の余地

今回の `cmd/storybook` には入れていないが、`minigo` をホスト側で組み込む形を取ると、アプリ側のコードを変えずに実行環境を差し替える方向も試せそうに見えている。

- **標準ライブラリ binding の差し替え**: `Engine.Bind` や `Engine.BoundOf` を使うと、ホスト側の binding を差し替えて現在時刻を固定したり、外部 I/O に決まった結果を返させたりできる（`ModeSource` は binding を迂回するため実行モードの考慮や、コンパイル済みホスト実装の内部呼び出しには効かない境界はある）。
- **ソース関数の部分差し替え（今後のアイデア）**: 現在はパッケージ全体の host binding 登録しかできないが、元のソースを残したまま `loadUser(id)` のようなデータ取得関数だけを外から fake に差し替えられれば、render 関数を切り出していない既存アプリに `interface` を足さずに状態を再現できる余地がありそうである。

このあたりは、単なる Go テストにはない `minigo` ならではの実験テーマとして面白そうな部分だと考えている。

## 5. 試してみて見えたギャップと、次に確認したいこと

この構成で「Story を書いてブラウザで HTML を表示する」流れ自体は動くようになったが、本来の目的である「実ブラウザで CSS やレイアウトを調整する作業」に使うには、まだ大事なところが足りていないと感じている。

- **実アプリの CSS が当たらない**: 今のサンプルの HTML は自己完結させており、`/static/app.css` のような外部アセットを元のパスと同じ形で配信する仕組みがない。実際の調整作業ではここが必須になりそうである。
- **エッジケースの fixture を手書きするのが重い**: 本当に見たいのは、0 件・1 件・大量、改行できない長い英単語、任意フィールドの欠落、画像なし、多言語混在といった状態である。既存アプリの表示用構造体は深く入れ子になりがちで、毎回手書きするのは負担になりそうだと感じる。
- **状態違い・画面幅違いを並べて比べられない**: CSS の変更は複数状態に同時に効くため、1 Story ＝ 1 ページで開くより、同じテンプレートの状態違いや viewport 幅違いを一画面に並べて比較できる方が調整しやすいはずである。
- **変更の種類に応じた再実行の軽さ**: CSS だけの編集ならブラウザの再読み込みで済んでほしく、テンプレートや Go コードを変えたときだけ `minigo` の再実行が走る形が自然である。

次に進めるなら、いきなり抽象的な機能を足すのではなく、実際の作業に近い順で試してみたい。

1. 静的アセット（CSS など）の配信と、状態違い・画面幅違いの並列プレビューを足して、実際に CSS を直す作業で使ってみる。
2. fixture の手書きが本当に負担だと感じたら、render 関数や HTML ツリー関数の引数の型から「空・最小・最大・長文」の値を生成する仕組み（必要なソースだけ読む `minigo` と相性が良さそうだが未検証）を試してみる。
3. 既存アプリに手を加えず動かす必要が強ければ、ソース関数の部分差し替えや標準ライブラリ binding の差し替えを具体的に検討する。
