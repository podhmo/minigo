# M6 の判断記録

M6 の各項目は「検討する（判断して記録する）」タスク。ここに判断と根拠を残す。

## M6-1 コンパイル済みコードの共有

**判断: 現状では Chunk を Session 間で共有できない。共有する方向は M5（PackageImage / PackageInstance の分離）の延長として成立するが、ガードの追加と分割が必要。**

Chunk のフィールドを「共有できるもの」と「Session 依存のもの」に分ける:

共有できるもの（純粋なコンパイル産物）:

- `Code`, `NLocals`, `NParams`, `NResults`, `NamedSlots`, `Upvals`, `IsVararg`
- `Boxed`（P4-2 のスロット分類）、`Escapes`（P4-2 のメモ）
- `Sites` の器自体（`*GlobalSite` はガード付きキャッシュであり、保持する値は VM 側の型で Session を参照しない）

Session 依存のもの（共有を阻むもの）:

- `Consts`: `OpConst` 系が `Pkg`/`File`/`Binds`/`LocalTypes` 付きの `*runtime.TypeDef`（compile/expr.go の mint）を入れる。`OpMakeClosure` はコンパイル時の `*runtime.Function`（`c.constIdx(inner)`）を入れる。`OpEvalFragment` の `*ASTFragment` は session 側で parse した `*syntax.File` を保持する。typedef の intern 表は Session 単位（M4-3b）なので、別 Session で同じ型を指すポインタが一致しない。
- `CallSites`: deferred fact の `TypeRef`/`TypeDef` が session の intern・index 経路に解決される。
- `Sites` の `selectSlot`（P4-5b）: `res.m` は解決した Session が compile した `*runtime.Function` で、その `Pkg` は呼び出し元 Session の `PackageInstance` を指す。ガードは `(TypeID, MethodSetEpoch)` のため、別 Session に chunk を渡すと Session A の method オブジェクトが Session B の実行に bind され、A の globals を読む — `globalSlot` のような `(env, gen)` ガードはない。共有するなら同様の env/pkg ガードを足す必要がある。

共有するための条件（M5 の方向と一致）:

1. typedef intern 表とコンパイル済み `*runtime.Function` を不変の `PackageImage` 側へ移す（`PackageInstance` に exec 状態だけ残す分割の延長）。
2. `CallSite` の session 依存参照を残さない、または遅延解決に寄せる。
3. `selectSlot` に `(env/pkg, epoch)` ガードを追加する（`globalSlot` と同型）。

動機の評価: `NewSession` は約 16µs（`BenchmarkReloadStages/Session`）で、遅延 install の効果で起動コストは既に小さい。共有の主目的はコンパイルそのものの重複回避になるが、そのボトルネックは parse 側にある（M6-3 の節）。**今は共有しない。** PackageImage への intern 移行が実装された段階で再検討する。


## M6-2 Session 間での bind テーブルの共有

**判断: 実施しない。** ゲート条件「遅延 install のあとでもセッションの起動コストが大きい場合に限る」に対し、現行の計測では `NewSession` が約 16µs・119 allocs（`BenchmarkNewSession`/`BenchmarkReloadStages/Session`）で、起動コストは支配的ではない。`bind.Env` を呼び出しコンテキストへ移す設計変更に見合う動機がない。起動コストが問題として再浮上した場合に再検討する。

## M6-3 シンボル単位の materialize

**判断: 実施しない。** ゲート条件「realworld で parse/index が支配的な場合に限る」への根拠として `BenchmarkReloadStages`（12 ファイルのパッケージ、resolver warm）を計測した:

| stage | ns/op | 占率 |
|---|---|---|
| LocateDir | ~483k | ~20% |
| Parse | ~1.7M | ~74% |
| Index | ~76k | ~3% |
| NewSession | ~16k | ~1% |

parse が支配的であることは確認できたが、index が全ファイルの AST を要求する構造上、シンボル単位の materialize では支配コスト（parse）を削減できない — materialize は index の下流であり、すでに遅延 install で未使用シンボルの runtime 化は遅延済み。残る支配コストは parse で、これは per-symbol lazy では除去できない。**ゲート条件の判定材料としては realworld 計測が望ましいが、設計上の上限（index が全 AST を要する）から効果は限定的と判断する。**

## M6-4 tagged `Value`

**判断: やらない（既定どおり）。** ゲート条件「P4 のあとも boxing が単独で約 15% を超える場合」に対し、P4-2c 後の分類では boxed slot が 5.9%・escape chunk が 9.1%。`BenchmarkGenericCall` の alloc profile でも Cell（boxing）由来の alloc は上位に現れず、generic 系（`specializeType` ~20% flat、`instantiate` ~70% cum、`typeIDOf` ~12%）が支配的で、boxing は 15% に達しない。tagged `Value` 導入の動機がない。
